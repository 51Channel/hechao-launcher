# 常见错误与处理

## 1. 每个活动都去改启动器 UI

**错误原因**：当前启动器由服务器目录和客户端档案驱动，活动卡片不是写死列表。

**正确做法**：创建或更新签名 `profileId`，再用后台目录记录绑定显示名、版本、权限、
排期和 `velocityTarget=activity`。只有平台契约表达不了通用需求时才改启动器/API。

## 2. 继续把活动接到 Survival2

**错误原因**：这是旧替换服结构，会让生存服和活动服共享错误的路由与状态。

**正确做法**：所有新活动和改版统一使用 `activity`；旧 `dollnight -> survival2` 需要
独立迁移，不复制。

## 3. 两个活动目录同时设 Online

**错误原因**：它们最终共享同一个 Velocity `activity` 目标，授权不能区分两个同时运行
的 `25568` 后端。

**正确做法**：旧、新活动先都设 Maintenance，停止旧后端、启动并验收新后端，最后只
开放一个记录。

## 4. 原生 NeoForge 上继续复制 Bukkit 插件

**错误原因**：原生 NeoForge 不加载 Bukkit 插件。混合核心会增加映射、事件和性能风险。

**正确做法**：把服务端功能实现为 NeoForge 模组，或者选择 Paper/Purpur 的纯插件活动。
必须混合时先单独评估和批准，不把它当默认能力。

## 5. 客户端限制三次就认为安全

**错误原因**：修改客户端可以绕过按钮、冷却和本地计数。

**正确做法**：客户端负责体验，服务端再次验证次数、序号、阶段和位置。取消固定、死亡、
换回合或重连时由服务端重置状态。

## 6. 把世界逻辑全部改成异步

**错误原因**：Minecraft 世界、实体、库存和计分板通常不是线程安全对象，会产生崩溃、
丢数据或难以复现的竞态。

**正确做法**：异步只做有界 I/O 和不可变快照纯计算，结果回到主线程再次验证并应用。
物资生成使用每 tick 预算队列。

## 7. 通过缩小半径解决卡顿

**错误原因**：这改变玩法，且可能掩盖真正的实体 AI、区块加载、同步 I/O 或分配热点。

**正确做法**：先用 JFR/兼容分析器和 TPS/MSPT/GC 证据定位，再做批处理、缓存、限流、
逐 tick 生成或算法优化。玩法参数变化单独审批。

## 8. 开会把所有玩家传到同一点

**错误原因**：碰撞、窒息和实体推挤会造成卡死或死亡。

**正确做法**：预计算多个安全落点，服务端线程逐个复核地面、空间、边界和占用，再分散
传送；必要保护时间必须可配置且有测试。

## 9. 只隐藏一次 nametag

**错误原因**：登录、重生、换世界、队伍变更或其他 TAB/计分板组件会重新写回。

**正确做法**：指定唯一所有者，在生命周期事件上幂等重应用，并审计冲突插件/模组。

## 10. 部署完成就顺手开服

**错误原因**：部署、启动、目录 Online 和灰度是不同风险动作；当前平台遵循手动开服。

**正确做法**：部署后保持停止并报告可启动。获得当前任务明确授权后，使用后台结构化
启动，让冲突编排先停同槽后端。

## 11. 把“命令成功”当成验收

**错误原因**：计划任务可以成功返回，但 Java 可能立即退出、端口被错误进程占用或加载
了旧 JAR。

**正确做法**：核对 PID、祖先、工作目录、监听、日志版本、心跳、TPS/MSPT/GC，并用
正确和错误客户端各走一次真实授权。

## 12. 从旧服务端无差别融合插件和配置

**错误原因**：旧公告、墓碑、TAB、nametag、命令或世界插件会与活动玩法冲突。

**正确做法**：发布说明明确 `replace` 或 `overlay`，对受管 `mods/plugins/config` 使用
白名单和哈希；保留项逐个声明，默认不继承未知功能。

## 13. 把“赫朝基础插件”理解成一个通用 plugins 文件夹

**错误原因**：Velocity Authorizer 是代理单例，Lobby Guard 和 LuckPerms Tier Agent
只属于内部大厅，ServerControlAgent 和 StatusCollector 属于 VPS 主机。它们不是每个
后端都要复制一份的 Bukkit 插件。

**正确做法**：按 `docs/HECHAO_NEW_SERVER_BASELINE.md` 建立组件计划。新后端只安装与
真实加载器和版本精确兼容的 forwarding、指标实现和活动自有组件；主机能力通过目标
注册，平台单例与大厅组件只核验或明确排除。
