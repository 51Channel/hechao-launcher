# 从这里开始

这是一份可离线阅读的赫朝 Minecraft 活动开发交接包。它解决的是“新开发者和新的
Codex 如何沿用当前平台”，不是替代 Git 仓库、管理员后台或生产凭据。

## 还没有活动名称、源码或目标时

本包也支持“纯规范接管”。此时负责人不需要临时编造活动名、仓库或需求，也不需要先
创建空项目。让接手 Codex 使用 `01-给Codex的首条消息.md` 中的“模式 A”，完成以下
工作即可：

1. 阅读活动通道和新服务端基础组件规范；
2. 复述固定路由、活动槽、档案隔离、组件分层、手动开服和 Git 边界；
3. 说明未来真正开工时需要负责人提供哪些信息；
4. 保留空白需求单和组件计划模板，不连接生产、不创建假源码、不部署任何 JAR。

等具体活动出现后，再使用“模式 B”进入实际开发。缺少当前项目不代表交接失败；它只
表示现在应验收规范理解，而不是验收代码。

## 给同事的 10 分钟接入流程

1. 核对 ZIP 同名 `.sha256`，再解压到一个新的空目录。
2. 在 Codex 中打开解压后的根目录，不要只上传单独一篇文档。
3. 让 Codex 先读取根目录 `AGENTS.md`。
4. 打开 `01-给Codex的首条消息.md`。当前只有规范时使用模式 A；已有真实活动时填写
   模式 B 的活动名、源码路径和本次目标后发送。
5. 和 Codex 一起填写 `02-新活动需求单模板.md`；不确定的易变事实让 Codex实时核验。
6. 让 Codex 复述以下架构链路，确认理解后再改代码：

```text
活动源码
  -> 基础组件计划
  -> 服务端发布
  -> 独立客户端档案
  -> Test / Gray / Production
  -> 启动器目录记录
  -> 一次性进服授权
  -> Velocity activity
  -> owl5 127.0.0.1:25568 当前唯一活动后端
```

7. 第一个任务使用包内“集合签到”案例，或选择一个不涉及世界破坏的同等级小功能。
8. 本地构建、专用服务端和双客户端通过后，才讨论客户端档案和 VPS 部署。
9. 生产部署、生产启动、目录 Online 和人数灰度是四个独立动作，不一次性全做。
10. 最后要求 Codex 按 `05-最终交付报告模板.md` 交付，并检查 Git 已推送。

## 负责人需要另外提供

- 实际活动源码仓库路径或 Git 地址；
- 本次是“新活动”还是“现有活动兼容修复”；
- 玩法需求、目标人数和活动日期；
- 是否允许修改客户端档案、服务端、后台目录和服控模板；
- 是否仅部署，还是明确允许启动生产活动服；
- 地图来源和授权、旧世界是否保留、回滚目标；
- 需要进行真人灰度时的账号和参与人员安排。

生产凭据不放进交接包或需求单。需要生产操作时，使用该机器已有的受控登录状态、密钥
存储和管理员 MFA，由负责人在当前任务中明确授权。

## 如何判断 Codex 已经理解

开始编码前，它应能准确回答：

1. 玩家入口为什么固定是 `activity`，而不是 `survival2`？
2. 为什么不同活动能共享 Velocity 目标，却不能同时运行两个 `25568` 后端？
3. 什么情况升原 `profileId` 版本，什么情况必须新建档案？
4. 为什么客户端禁用按钮不能代替服务端权限校验？
5. 哪些工作可以异步，哪些 Minecraft API 绝不能放到后台线程？
6. 为什么部署完成后默认保持停服？
7. 客户端、服务端和目录分别如何回滚？
8. 哪些基础组件属于 Velocity、内部大厅、VPS 主机和游戏后端，为什么不能整目录复制？

回答不完整时继续阅读规范和案例，不要靠猜测进入生产。
