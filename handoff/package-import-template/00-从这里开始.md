# 从这里开始

## 目标

本包解决的是“怎样制作赫朝后台真正能消费的双端整合包”。它不代替活动源码、Minecraft
许可证核对、专用服务端测试或生产审批。

最终业务链路是：

```text
活动源码与上游文件
  -> 完整客户端源 + 完整服务端源
  -> 赫朝规范化上传 ZIP
  -> 后台识别并拆成 client.zip / server.zip
  -> 客户端 Test 发布 + 服务端制品入库
  -> 客户端推进 Production
  -> 日历企划绑定整合包
  -> 停服部署到唯一 activity 槽
  -> 管理员在开放窗口前启动
```

## 给同事的 15 分钟接入流程

1. 将本交接 ZIP 解压到新的空目录，在 Codex 中打开整个目录。
2. 让 Codex 先读根目录 `AGENTS.md`，再发送 `01-给Codex的首条消息.md` 中的模板。
3. 提供真实活动源码、客户端源、服务端源、Minecraft/加载器/Java 版本和地图来源。
4. Codex 先盘点文件和许可证，再创建一个不含秘密的规范源目录。
5. 使用 `templates/` 中的示例填写两个 JSON；示例使用 `.example` 后缀，不能直接上传。
6. 运行本地校验。任何错误都修源文件，不在后台强行跳过。
7. 在独立测试目录完成客户端启动和专用服务端启动；测试结束后安全停服。
8. 生成业务 ZIP、SHA-256 和报告。交付前重新从 ZIP 解压并抽查文件。
9. 管理员默认选择“仅发布并入库”，不要用“立即部署”替代企划流程。
10. 后台动作、Production 推进、企划发布、服务端部署和服务端启动分别审批。

## 开工前必须取得的信息

- 活动显示名和稳定 `activityId`；
- 是新活动、兼容修复还是不兼容升级；
- Minecraft、加载器、加载器版本和 Java 主版本；
- 客户端实际版本目录名 `versionId`；
- 客户端和服务端上游来源、许可证与精确版本；
- 哪些 JAR 是客户端专用、服务端专用或两端共用；
- 地图来源、是否随包部署、是否保留旧世界；
- 目标人数、内存建议和专用服务端测试结果；
- 回滚客户端版本、服务端制品和世界备份；
- 本次是否仅制作，还是允许测试上传或生产操作。

信息缺失时应明确列为阻断项，不能用示例值生成“正式包”。

## 最容易混淆的三件事

1. `hechao-pack.json` 描述上传包；`client/hechao-profile.json` 描述客户端如何启动。两个
   文件都需要，字段含义不同。
2. `shared/` 不是“暂时不知道放哪”。其中每个文件都会被复制到客户端和服务端。
3. 日历只自动控制准入窗口，不自动启动或停止 Minecraft。整合包部署后也保持停服。
