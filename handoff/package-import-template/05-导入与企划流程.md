# 导入与企划流程

制作完成不等于活动上线。标准操作顺序如下：

1. 在 Launcher 后台“整合包导入”上传业务 ZIP。
2. 等待识别完成，核对布局、Minecraft、加载器、Java、客户端/服务端文件数、警告和文件
   抽样。存在 `Blocking` 时修复源包并重建，不能跳过。
3. 填写稳定档案 ID、显示名、SemVer、最低称号、内存和世界策略。
4. 新企划默认选择“仅发布并入库”。Publisher 只创建客户端 `Test` 发布，服务端制品留在
   受限存储，不覆盖活动槽、不启动 Minecraft。
5. 在独立账号和机器完成 Test 客户端、服务端及玩法验收，再把该精确清单推进
   `Gray -> Production`。不能用另一个同版本清单代替。
6. 在 Launcher 后台或官网后台的活动企划日历创建草稿，绑定已完成整合包并设置半开区间
   `[开始, 结束)`。
7. 发布企划。已发布区间不能重叠；同一时刻最多开放一场活动。
8. 活动槽停止、代理在线且无其他操作时，从企划页执行 `DEPLOY <planId>`。部署完成后
   服务端仍保持停止，并由心跳报告精确整合包身份。
9. 在开放窗口前由管理员按服控流程启动。开放时间到达后，只有企划已发布、客户端为
   Production、服务端在线、心跳新鲜且部署身份完全一致时才能进入。
10. 结束时间到达后准入自动关闭，但 Minecraft 不会被日历自动停止；管理员安全停服。

## 四个入口的数据关系

- Launcher 后台和官网后台编辑同一份 Launcher PostgreSQL 企划数据。
- Launcher 活动页展示企划并提供客户端下载。
- 官网社区日历只展示脱敏时间和公开信息，不提供整合包下载。
- 客户端本地安装状态只存在于 Launcher。

## “立即部署”活动槽

该选项只保留给旧导入流程。它会把客户端发布和停服部署串在同一导入任务中，但仍不会
启动服务器。新活动应先入库，再从日历绑定和部署，便于审计、换包和排期冲突检查。

## 回滚分层

- 客户端：把通道退回上一份未暂停的签名清单。
- 服务端：停服后恢复代理保留的上一服务端目录或明确制品。
- 世界：按独立正式备份恢复，不能把服务端目录回滚当作唯一世界备份。
- 企划：撤回或改期；不要删除数据库记录绕过审计。
- 回滚后不会自动启动旧活动，仍需管理员明确选择。
