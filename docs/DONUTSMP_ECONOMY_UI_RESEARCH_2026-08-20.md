# DonutSMP 经济系统与 UI 交互研究

- 研究日期：`2026-08-20`
- 适用项目：天域远征工业季经济与第三方 Screen
- 研究目的：提取成熟服务器的经济分层、价格发现和菜单交互方法，作为赫朝实现参考
- 当前边界：本次只更新研究文档，不修改 API、插件、客户端代码，不上传 OSS，不操作生产服务

## 1. 结论摘要

DonutSMP 的关键不在于某一张价格表，而在于把不同交易意图拆成不同入口：

1. 服务器固定回收：玩家快速清理物资，获得最低但确定的流动性。
2. 服务器商店：玩家用金币购买基础物资，承担货币销毁和价格锚定作用。
3. 玩家市场（Auction House）：卖家自由定价，买家主动浏览，形成公开的卖方报价。
4. 求购订单（Orders）：买家先报出愿意支付的单价和数量，卖家直接履约，形成公开的买方报价。
5. 独立碎片货币：服务于稀有奖励或生成器，不与主货币混兑，避免所有价值压到一条余额曲线上。

这几条链路的职责不能合并成一个“大面板”。赫朝后续应优先实现真正的订单簿和清晰的
`/sell`、`/prices`、`/shop`、`/ah` 分工，再做碎片货币和高级统计。

## 2. 资料可信度

### 2.1 官方公开 API（高可信）

实时核对了 DonutSMP 公共 Swagger：

- [Swagger UI](https://api.donutsmp.net/v1/)
- [OpenAPI/Swagger JSON](https://api.donutsmp.net/v1/doc.json)
- [公开 API 文档源码](https://github.com/numenmc/donut-api-doc)

文档明确说明这是 Official Public API；游戏内通过 `/api` 创建 Key，每个 Key 当前限制为
`250 requests/minute`。本项目没有申请、保存或使用 DonutSMP Key。

已确认的经济相关公开接口：

| 接口 | 公开内容 | 可用于推导的产品能力 |
| --- | --- | --- |
| `/v1/auction/list/{page}` | 当前挂单、物品、卖家、价格、剩余时间 | 玩家市场列表、搜索、排序、过期提示 |
| `/v1/auction/transactions/{page}` | 最近已售出的物品、价格、卖家、售出时间 | 成交历史和真实成交行情 |
| `/v1/stats/{user}` | 余额、碎片、`money_made_from_sell`、`money_spent_on_shop` 等统计 | 资产/行为总览 |
| `/v1/leaderboards/money/{page}` | 余额排行 | 财富排行 |
| `/v1/leaderboards/sell/{page}` | `/sell` 累计收入排行 | 服务器回收产出统计 |
| `/v1/leaderboards/shop/{page}` | `/shop` 累计消费排行 | 服务器商店货币销毁统计 |
| `/v1/leaderboards/shards/{page}` | 碎片排行 | 独立货币排行 |

官方公开 API 的 Auction House 列表页有以下明确合同：

- 每页返回 `44` 个位置；不足部分用 `null` 填充。
- 请求可携带 `search` 和 `sort`。
- `search` 可匹配玩家名、物品 ID 和显示名（适用时）。
- 公开排序值为 `lowest_price`、`highest_price`、`recently_listed`、`last_listed`。
- 交易历史每页 `100` 条，最多读取 `10` 页，按售出时间排序。
- 物品公开结构包含 ID、显示名、数量、Lore、附魔和容器内容等字段。

这些接口能证明 DonutSMP 重视“挂单”和“成交”两个不同数据集；不能证明其内部数据库、
税率或所有 GUI 行为，后者不能从公开 API 反推。

## 3. 经济闭环

### 3.1 价格发现的四个角色

| 入口 | 谁决定价格 | 玩家意图 | 经济作用 |
| --- | --- | --- | --- |
| `/sell` | 服务器 | 现在就把物资换成钱 | 提供流动性，但也是主要发币口 |
| `/shop` | 服务器 | 立即买到基础物资 | 货币销毁、应急供应、价格上锚 |
| `/ah` | 卖家 | 等待买家按我的价格购买 | 形成卖方报价和稀有物品市场 |
| `/orders` | 买家 | 我愿意按这个单价收多少 | 形成买方报价，适合大宗农产和矿物 |

理想关系不是固定倍数，而是动态区间：

```text
服务器回收价 <= 求购成交价 <= 玩家市场常见成交价 <= 服务器商店售价
```

这只是首期调价的安全方向，不是所有物品永远都必须满足的硬规则。稀有装备、复杂模组
物品和高阶机器可以只开放给玩家市场，避免服务器直接出售破坏稀缺性。

### 3.2 为什么必须有订单簿

只有 `/ah` 时，玩家必须先上架，再等待别人浏览；农场玩家有大量同质物品时，操作成本高，
而买家也无法表达“我愿意按某价格大量收购”。`/orders` 把需求提前公开：

1. 买家选择物品，填写单价、数量上限和有效期。
2. 服务端冻结买家所需的最高金额，订单进入订单簿。
3. 卖家浏览订单，选择全部或部分履约。
4. 服务端原子扣除卖家物品、减少订单剩余数量、支付卖家并写入交付记录。
5. 取消或过期时退回未使用的冻结金额。

订单和 AH 的价格都应以已成交数据为准。未成交的极端挂单不能直接进入 K 线或“市场均价”，
否则玩家可以用一个虚高挂单制造假行情。

### 3.3 货币和反通胀

DonutSMP 公开资料把 money 和 shards 分成两个用途不同的货币。对赫朝而言，至少应有：

- 服务器回收发币额度：按物品、玩家和全服分别限制，并支持跨商品金额封顶。
- 服务器商店销毁：基础物资售价必须从账本扣除，不绕过统一经济服务。
- AH 上架费和成交税：作为持续销毁渠道，具体比例以真人数据调整。
- 订单冻结余额：冻结不等于销毁，取消/过期必须可审计退回。
- 物品消耗：修理、领地、机器维护、活动门票等长期消耗比单纯税费更能稳定经济。

## 4. DonutSMP 可见 UI 交互

### 4.1 总体风格

公开订单演示显示的是 Minecraft 原生箱子菜单：标题栏、物品图标网格、Lore 详情和底部
控制槽，而不是网页式大卡片或一整块背景文字。订单缩略图可见类似
`ORDERS (Page 1/20)` 的标题、密集物品图标和底部导航/操作槽。

这套交互的优点：

- 玩家已经熟悉 9x6 背包网格，不需要学习新的控件语义。
- 物品图标天然表达商品，Lore 只承载价格、数量、卖家和时间。
- 分页、返回、刷新、创建和“我的订单”都有稳定槽位。
- 点击物品进入确认，而不是把所有说明堆在主列表上。

### 4.2 推荐的赫朝菜单骨架

所有列表型经济页面统一使用 54 槽语义：前 45 槽放业务条目，最后一行固定放控制项。
客户端可以继续绘制工业风背景和模块边界，但不能改变槽位的任务含义。

底部控制行建议固定为：

```text
上一页 | 筛选/搜索 | 当前页 | 排序/刷新 | 我的挂单/订单 | 待领取 | 返回
```

不同页面只替换中间的业务条目，避免玩家每次换页面都重新寻找按钮。

### 4.3 各入口交互

#### 余额 / 个人账户

首页不只显示一个金币数字，建议分为四个明确状态：

- 可用余额；
- 已冻结（订单和待结算操作）；
- 待领取物品/待结算收入；
- 今日发币、消费和市场净流入。

点击余额进入交易历史，历史条目必须显示方向、金额、来源、时间和结果状态。网络失败时
显示“最后同步时间”，不能把缓存余额伪装成实时可交易余额。

#### `/prices` 服务器回收目录

这是“查价格”的目录，不应直接等同于出售操作。每个物品条目只显示：物品图标、单位回收价、
剩余数量/金额额度、来源标签和“放入出售”动作。搜索应支持中文名、注册 ID 和命名空间。

#### `/sell` 快速出售

这是任务型页面，不是商品展览页：

1. 玩家把物品放入输入槽；
2. 立即显示数量、单位价、预计收入和剩余额度；
3. 点击确认后再次校验物品快照；
4. 成功、明确失败、结果未知分别显示不同状态；
5. 失败或断线时物品进入补偿邮箱，不能掉落到世界。

#### `/shop` 服务器商店

分类、搜索、数量步进、总价、余额和确认购买必须在同一流程内；购买完成后显示余额变化。
服务器商店不要和回收目录共用同一标题或按钮，否则玩家会误以为“查看回收价”会直接扣钱。

#### `/ah` 玩家市场

建议分成四个标签，而不是把所有功能挤在一个列表：

1. 浏览市场；
2. 我的挂单；
3. 待领取；
4. 成交记录。

浏览列表的每个条目显示物品、数量、总价、单位价、卖家、剩余时间；排序至少包括最低单位价、
最高单位价、最新上架和即将过期。点击条目进入确认页，确认页只保留物品、价格、余额变化和
确认/返回两个动作。

#### `/orders` 求购订单

建议分为：

1. 浏览求购：按物品、单价、剩余数量和到期时间排序；
2. 创建求购：选择物品、填写单价、数量、有效期，预览冻结金额和手续费；
3. 我的求购：追加数量、取消、延长或查看履约记录；
4. 可履约：从玩家背包选择数量，预览本次收入后确认交付；
5. 历史：已完成、已取消、已过期。

订单条目的 Lore 不超过可扫描的几行：

```text
物品：小麦
单价：0.75 金币
剩余：3,200 / 5,000
求购者：玩家名
剩余时间：2 小时 14 分
点击：履约 / 查看详情
```

创建和履约都要有二次确认；处理中时锁定按钮，避免重复点击。部分履约必须是正常状态，
不能强迫玩家一次凑齐全部数量。

## 5. 与赫朝当前实现的对照

### 已具备的基础

- `/ah` 玩家市场浏览、上架、我的挂单、购买、下架和待领取；
- 搜索、分页、普通物品托管、上架费和成交税；
- 服务端事务、幂等操作、失败补偿和按服务器隔离；
- NeoForge 原生 Screen 与上架页布局契约；
- 85 项官方回收目录和服务端模糊搜索。

### 与成熟闭环仍有差距

1. 没有独立 `/orders` 买方订单簿、冻结余额和部分履约流程。
2. `/shop` 仍处于回收目录过渡语义，服务器购买商店尚未形成独立合同。
3. 玩家可见的成交历史、挂单成交统计、单位价排序和真实成交行情还不完整。
4. 余额页面需要区分可用、冻结、待领取，而不是只显示一个金币数字。
5. 复杂 Data Components/NBT 和模组能力物品仍不能安全托管，不能直接照搬原版 AH 体验。
6. 当前自定义 Screen 的视觉层仍应服从箱子菜单的任务结构；背景只做氛围，不能替代物品槽、
   操作模块和状态反馈。

## 6. 推荐实现顺序

### 阶段一：先把现有 `/ah` 做成可用市场

- 增加最低/最高单位价、最新上架、即将过期排序；
- 增加成交历史和我的成交记录；
- 首页余额改成可用/冻结/待领取三项资产摘要；
- 固化 54 槽控制行和统一确认/加载/未知结果状态；
- 完成双真人账号的购买、下架、领取、断线和余额守恒门禁。

### 阶段二：实现 `/orders`

- 新增订单、订单履约、订单交付和冻结余额数据模型；
- 支持部分履约、取消、过期退款和离线领取；
- 所有写操作使用幂等键，订单、余额、物品和审计在同一事务边界内裁决；
- 先只开放无复杂组件的标准物品，按 2/3/5/20 人灰度。

### 阶段三：拆分 `/prices` 与真正 `/shop`

- 旧回收目录迁移到 `/prices` 或明确的“服务器回收”入口；
- `/shop` 只负责服务器出售和金币销毁；
- 服务器商品售价、回收价和玩家市场价格分开统计，避免后台 K 线混淆。

### 阶段四：碎片和经济分析

- 碎片作为独立账本和独立商店，不允许隐式兑换金币；
- 展示真实成交量、中位价、成交额、订单深度和货币净增量；
- 至少积累 7 天真人数据后再调价，不追随单个极端挂单。

## 7. 上线验收门禁

- 两个真实账号同时创建、浏览、履约、购买、取消和领取；
- 订单部分履约、库存不足、背包已满、订单过期和取消退款；
- 断线、超时、重复点击、重复请求和服务重启后查询原操作状态；
- 买家余额、卖家收入、冻结余额、手续费、税费和待领取物品守恒；
- 同一玩家不能购买自己的挂单或履约自己的订单；
- 未成交挂单不进入成交 K 线；
- 复杂 NBT、命名、附魔、容器和模组能力物品明确拒绝并可恢复；
- UI 在加载、空列表、搜索无结果、错误和结果未知时都保持可操作，不闪回游戏画面。
